# Как внести вклад в StackMIREA

Спасибо, что помогаете развивать проект. Здесь можно улучшать учебные материалы, интерфейс, поиск, навигацию, контентный pipeline и CI.

Перед началом ознакомьтесь с [кодексом поведения](./CODE_OF_CONDUCT.md). Уязвимости отправляйте по процессу из [SECURITY.md](./SECURITY.md), а общие вопросы — по инструкции из [SUPPORT.md](./SUPPORT.md).

## Подготовка окружения

Понадобятся Git и Node.js 20 или новее.

```bash
git clone https://github.com/minkinad/StackMIREA.git
cd StackMIREA
npm ci
npm run dev
```

Локальный сайт откроется на <http://localhost:3000>.

## Выберите тип изменения

### Учебный материал

Редактируйте только исходники в `docs/`. Файлы `.cache/content-manifest.json` и `public/search-index.json` создаются автоматически.

У каждой страницы должны быть метаданные:

```yaml
---
title: Название материала
description: Краткое и конкретное описание страницы.
author: github-login
order: 1
---
```

Вместо `order` можно использовать `sidebar_position`. Для нового учебного трека добавьте запись в `lib/tracks.json` и индексную страницу `docs/<track>/index.mdx`.

Хороший материал:

- объясняет цель и ожидаемый результат;
- содержит воспроизводимые шаги и проверенные примеры;
- указывает язык у каждого блока кода;
- ссылается на источники и локальные ресурсы относительными ссылками;
- не включает секреты, персональные данные и непроверенный исполняемый код.

После изменений запустите:

```bash
npm run quality
npm test
```

### Код и интерфейс

Сохраняйте существующие соглашения проекта: TypeScript в строгом режиме, App Router, функциональные React-компоненты и utility-классы Tailwind CSS. Не добавляйте зависимость, если задачу можно решить средствами текущего стека.

Минимальные проверки:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Если изменение затрагивает чтение, поиск или рендер контента, дополнительно запустите `npm run quality`.

### Скрипты и CI

Для изменений в `scripts/` добавляйте или обновляйте тесты в `scripts/content-quality/__tests__/`. Для workflow сохраняйте минимальные разрешения и не помещайте секреты в репозиторий или логи.

Проверяйте команды в том же порядке, в котором они выполняются в `.github/workflows/`.

## Рабочий процесс

1. Создайте ветку от актуального `main`.
2. Сделайте одно сфокусированное изменение.
3. Пересоберите генерируемые файлы штатными командами.
4. Запустите проверки для своей области изменений.
5. Просмотрите diff и убедитесь, что в нём нет случайных файлов.
6. Откройте pull request по шаблону проекта.

Понятный commit может выглядеть так:

```text
docs(python): добавить разбор регулярных выражений
fix(search): исправить поиск по границам слов
ui: улучшить мобильную навигацию
```

Строгий формат не требуется, но сообщение должно объяснять результат изменения.

## Pull request

В описании укажите:

- что и зачем изменено;
- какие страницы, треки или модули затронуты;
- какие проверки выполнены;
- скриншоты до и после, если менялся интерфейс;
- ограничения или решения, на которые стоит обратить внимание при ревью.

Небольшой, завершённый PR обычно проще проверить и безопаснее объединить, чем набор несвязанных изменений.
